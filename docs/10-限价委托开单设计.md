# 10 - 限价委托开单设计

> **状态**：2026-09-15 方案稿·OTO 修订（待拍板、待实施）
>
> **OTO 修订（2026-09-15）**：止损**随限价委托一并挂出**——`/fapi/v1/algoOrder` 支持 `algoType=OTO`（working 限价入场单成交 → 交易所自动激活 pending 止损单），裸仓窗口消除。原"SL 只能成交后挂、5 分钟裸仓窗口"的设计作废。
>
> **背景**：现行开仓唯一通道是"AI 分析落库 → 即时**市价**开仓"（[trade_engine.py:211](../backend/app/services/trade_engine.py)），AI 建议价只作闸门参考——现价偏离 AI 入场 >1% 直接作废（:139）。因此 AI 给出"回踩挂单入场"类建议时（如 VETUSDT 建议回踩 0.1629 企稳再进），系统不会真的挂单等待，交易直接流失。本方案引入**限价委托**：偏离带内的建议下限价单等待成交，成交后接入既有止损/止盈/结算状态机。
>
> **设计原则**：市价路径零改动（回归风险最小）；限价是**并列的新分支**，只复用既有闸门与成交后序列；DB 只加列不迁移；默认关闭，页面开关控制。

## 0. 拍板决策点（推荐值，可改）

| # | 决策 | 推荐 | 备选 |
|---|---|---|---|
| 1 | 分流规则 | 程序按偏离带自动分流：≤1% 市价、1%~3% 限价、>3% 作废 | AI 决策 schema 加 `order_type` 字段自主选择（P2） |
| 2 | 挂单时效 TTL | 24 小时 | 12h / 按K线根数 |

| 4 | 默认开关 | 关（`limit_order_enabled`，策略配置页开启） | 默认开 |
| 5 | SL 附带方式 | **OTO**（`algoType=OTO`，working=限价入场 + pending=STOP_MARKET closePosition 止损，成交瞬间交易所自动激活 SL）——裸仓窗口消除 | 巡检成交后手动挂 SL（原方案，作废） |

## 1. 分流规则（`_attempt_open` 内新增分支）

现价复核（方向-价格一致性、≤1% 偏离、RR 复算）改造为三分支：

```
dev = |现价 − AI入场价| / AI入场价
patient_side = (direction == long  and 入场价 < 现价×(1−0.001))    # 多单挂在现价下方等回踩
             or (direction == short and 入场价 > 现价×(1+0.001))   # 空单挂在现价上方等反抽

dev ≤ 1%                       → 市价路径（现状不变，按现价复算 RR）
1% < dev ≤ 3% 且 patient_side  → 限价委托路径（按委托价复算 RR ≥1.5）
其余（反向侧 或 dev > 3%）      → 作废（现状）
```

- **patient_side 约束**：限价买入价高于现价会被交易所立即吃掉（等效市价+更差滑点），必须严格挂在"等待回踩/反抽"的一侧；breakout 类建议入场贴近现价，天然落市价路径。
- **RR 复核口径**：限价路径按**委托价**复算（委托价 = AI 入场价，分析时 risk_guard 已验过，此处等价复验）；市价路径维持按现价复算。

## 2. 限价委托路径（下单序列）

1. **前置闸门全部复用**：max_open_trades（含 PENDING 计数，见 §5）、可用余额 ≥70%（委托锁定保证金）、资金分层、同币唯一、trade_type 开关、强平闸门、交易所精度。
2. **下单 = OTO 一体单**（新 trader 方法 `limit_order_with_sl`）：`POST /fapi/v1/algoOrder`，`algoType=OTO`——
   - **working 单**：LIMIT GTC，side=入场方向，price=委托价（=AI 入场价，经 `round_price` 取整），quantity=qty（固定亏损法，按委托价折算）；
   - **pending 单**：STOP_MARKET `closePosition=true`，side=反向，triggerPrice=AI 止损价（与市价路径同源）——**入场单满额成交的瞬间交易所自动激活该止损单**，无需等巡检；
   - 返回 OTO 父单 `algoId`。挂单被拒（-2021 止损触发价已在现价越过=前提漂移，-4120 精度）→ 与闸门失败同口径作废。
3. **落库**：`status='PENDING'`，`entry_price`=委托价、`stop_loss`/`tp1`/`tp2`=AI 三价（tp 用于前提失效检查）、`order_type='limit'`、`expires_at=now+LIMIT_ORDER_TTL_HOURS`、`raw.entry_order_id`=OTO 父单 algoId（复用既有字段）、`ai_snapshot` 照常。
4. **事件**：`LIMIT_PLACED`。**TP1/TP2 此时不挂**——未成交无仓位可保护，且 OTOCO 会被排除：其 OCO 语义（TP 成交自动撤 SL）与 TP1 成交后"SL 移保本 + TP2 继续挂"的状态机冲突，且两个 pending 位放不下 TP1+TP2+SL 三个单。止盈单由巡检在成交后挂（≤5min 延迟，无尾部风险——SL 已在场）。

## 3. 挂单巡检任务 `manage_limit_orders`

- **调度**：beat 每 5 分钟（`crontab(minute="*/5")`），Redis 锁 `lock:limit_manage`（与结算锁 `lock:trade_open` 独立——两者操作对象不重叠）。
- **输入**：全部 `status='PENDING'` 的 trade_records（testnet/正式网按各自 client）。
- **逐单处理**（顺序：先查单，再决策）：

| 情形 | 判定 | 动作 |
|---|---|---|
| 已过期 | `now > expires_at` | 撤 OTO 父单（`DELETE /fapi/v1/algoOrder`，[binance_trader.py:187](../backend/app/services/binance_trader.py) `cancel_order` 已有）→ CANCELLED（`exit_reason='limit_expired'`） |
| 完全成交 | OTO 状态 `FINISHED` 且仓位存在 | 成交后处理（§4）→ OPENED |
| 部分成交 | working 单部分成交 | **立即撤父单 + 市价平掉已成交部分** → CLOSED（`exit_reason='limit_partial'`）——OTO 的 SL 未激活前部分仓位无止损，风险必须有界 |
| 前提失效 | 未成交，多单现价 ≤ SL（止损区已到，入场前提死）/ 现价 ≥ TP1（已错过，不追）；空单对称 | 撤父单 → CANCELLED（`exit_reason='limit_premise'`） |
| 外部撤销 | OTO 状态 `CANCELLED`/`EXPIRED`/`REJECTED` | 对账 → CANCELLED |
| 继续等待 | 其余（WORKING 无成交） | 不动作 |

- **撤单-成交竞态**：撤单返回 -2011（可能已成交）或撤后复查已成交 → 一律按成交处理（§4），宁可开成不可开漏。
- **查单口径**：working 单在 `GET /fapi/v1/openAlgoOrders`（trader `open_algo_orders` 已有）；成交明细/最终状态查 `GET /fapi/v1/algoOrders?algoId=`。PENDING 期间 OTO 的 working+pending 两部分在交易所侧的可见形态（是否都出现在 openAlgoOrders）以 testnet 验证为准。
- **前提失效检查的开销**：每单一次 `price()` + 一次 algo 查询，挂单数量级 ≤ max_open_trades(10)，5 分钟一轮完全可承受。

## 4. 成交后处理（SL 已在场，只补止盈）

1. 查实际成交均价/量（algo 单成交明细的 avgPrice/executedQty，与市价路径 fill 查询同源）。
2. 挂 TP1（TAKE_PROFIT_MARKET reduceOnly 50%/75%）→ TP2（25%）——`_attempt_open` 现有 TP 挂单代码段复用（抽 `_attach_exit_orders(rec, fill_price, qty)` 共用）。
3. **TP 挂单失败回滚与市价路径同口径**：`cancel_all_algo` + reduceOnly 平仓（此时 SL 已在场，回滚更安全——先撤 algo 再平仓，无裸仓瞬间）。
4. **极端插针兜底**：OTO 激活的 SL 若成交瞬间触发价已被越过会立即触发市价平仓（交易所自动，等于插针保护内建）；巡检兜底——发现成交价已越过 SL 而仓位仍存活（SL 激活异常）→ 立即市价平仓 → CLOSED（`exit_reason='sl'`）。
5. 更新：`entry_price`=实际成交均价、`qty`=实际成交量、状态 OPENED、事件 `LIMIT_FILLED`。此后既有状态机（TP1_HIT 保本、移动止损、结算、`_rehang_lost_sl`）零改动接管。

## 5. 闸门与计数调整

| 闸门 | 调整 |
|---|---|
| max_open_trades | 计数 = OPENED/TP1_HIT/TP2_HIT + **PENDING**（委托锁定保证金，必须占名额） |
| 同币唯一 | **PENDING 也算**——挂单期间该币新分析不再开第二单（一个币一个计划） |
| TRADING_MIN_FREE_PCT | 不变（下委托前检查，交易所锁定保证金后自然反映在可用余额） |
| 开仓快筛（评分 ≥60、1h 内生成） | 不变（限价委托仍在分析落库瞬间放置） |

## 6. 与既有机制的交互

- **摘钩不删除**（重分析摘 `scan_result_id`）：PENDING 持有 `ai_snapshot` 快照，独立存活，不受摘钩影响。
- **结算巡检**（每小时 :10 `settle_trades`）：只处理 OPENED+，**不碰 PENDING**——职责分离，挂单生命周期完全归 §3 巡检。
- **复盘**（trade_reviews）：AI 建议回放与实际订单无关，不受影响。
- **A2 教训（SL 挂单巡检）**：PENDING → OPENED 转换后自动纳入既有 `_rehang_lost_sl` 巡检，无额外工作。

ALTER TABLE trade_records ADD COLUMN IF NOT EXISTS expires_at TIMESTAMPTZ;
-- status 列为 VARCHAR(16) 无约束，新值 'PENDING' / 'CANCELLED' 直接可用，无迁移

## 10. 行为变化（须知）

| 变化 | 后果 |
|---|---|
| "回踩挂单"类建议真的挂出去了 | 建议落地率上升；此前 >1% 偏离直接流失的交易现在进入等待队列 |
| 在跑名额被挂单占用 | 挂单期间同币不再重复开仓、名额 -1；若市场单边不回踩，名额到期才释放（TTL 内资金效率下降） |
| SL 由交易所 OTO 自动激活，裸仓窗口消除 | 挂单即带止损；残余窗口仅剩成交→巡检发现→挂 TP（≤5min，无尾部风险）；极端插针由 OTO 激活的 SL 立即触发兜底 |
| RR 复核口径分路径 | 限价按委托价（与分析一致）、市价按现价（更严）——同一建议两条路径的准入结果可能不同，属设计意图 |
| 委托锁定保证金 | 挂单期间可用余额下降，后续其他币开仓的 70% 余额闸门自然感知 |

## 12. P2 展望（本期不做）

- **user data stream**（listenKey WebSocket，ORDER_TRADE_UPDATE）：成交秒级感知 → TP1/TP2 即挂（消除 5 分钟止盈延迟）；repo 已有 kline_hub 的 WebSocket 基建可复用。SL 已由 OTO 交易所侧解决，不再依赖此流保命。
- **AI 自主选择委托方式**：决策 schema 加 `order_type: market|limit` + `ttl_hours`，AI 按形态性格（追突破 vs 等回踩）自选，程序只校验边界。
- **追价改单**：挂单跟踪现价（如始终挂在现价回踩 0.5% 处），到期或成交止。
