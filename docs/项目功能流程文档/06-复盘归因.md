# 06-复盘归因

> 现行版本：RULE_VERSION v2026-10-02（2026-10-02）。本文对照代码整理，以代码为准；历史拍板记录见 docs/archive/。

## 1. 概览

复盘系统的主轴是「实盘归因 → 补丁 → 规则演进」闭环（docs/archive/12，2026-09-18 拍板）：
复盘对象从「模拟回放 AI 建议」转向「实盘交易 + 计划对照」——每笔平仓单先做计划 vs 实际
对照与维度分组统计，再由 AI 出错误标签与教训，错误标签高频出现时自动生成规则补丁草稿，
人工确认合入后每日三态评估，最终通过 RULE_VERSION 递增把规则演进固化到每一笔数据上。

```
每小时结算巡检落库（trade_engine，docs/04）
        │ CLOSED + exit_reason
        ▼
费用回补 backfill_costs（惰性拉交易所 income）          ── backend/app/services/actual_review.py
        ▼
AI 错误归因（每小时 14 分，≤5 笔/轮）                   ── backend/app/services/ai_attribution.py
   程序算硬事实（MFE/MAE/入场位置）→ LLM 出标签+教训
        ▼                                    落库 error_tags / error_lesson / attributed_at
实盘归因统计 GET /review/actual              ── actual_review.build_actual_review
   总览 / 分组 / 逐笔计划 vs 实际
        ▼
补丁触发（每日 11:40 北京）                   ── backend/app/services/patch_service.run_trigger
   标签热度 ≥0.5 且样本 ≥8 → LLM 生成补丁草稿
        ▼
人工合入（页面按钮，即时生效）→ 每日 11:45 三态评估 → 有效定稿 / 无效定稿 / 恶化告警一键回滚
        ▼
规则集变更时人工递增 RULE_VERSION（config.py）→ 新开仓/分析行带新版本快照 → 复盘按版本分组隔离
```

**RULE_VERSION 分组机制**（docs/archive/24 A0，2026-09-29 拍板）：

- 定义在 `backend/app/config.py` 的 `RULE_VERSION`（现行 `v2026-10-01-3`）；注释约定改
  trigger / risk_guard / 提示词纪律 / 分批比例均算改版，须递增版本号。
- 开仓与 AI 分析时点快照：`trade_engine.py` 写 `trade_records.rule_version`，
  `ai_tasks.py` 写 `ai_analyses.rule_version`；NULL 旧行统一按 `legacy` 理解。
- 消费侧强制按版本分组：实盘归因分组维度含「规则版本」；
  `/review/stats` 输出独立的 `rule_version_groups`。
- 核心原则（docs/24 修订 v2）：历史交易跨多版规则，跨版本混合成绩不具证明力——
  「旧账不翻，新账记清」，跨版本混谈从机制上杜绝。补丁合入改变的是运行时规则
  （提示词覆盖段 / 参数列），RULE_VERSION 本身不自动 bump，需人工判断是否构成改版。

## 2. 实盘复盘统计

入口 `actual_review.build_actual_review(db, days, extra_filter)`（`backend/app/services/actual_review.py`），
API `GET /api/scans/review/actual`（`backend/app/api/scan.py`）直接返回 dict。统计范围为
`status=CLOSED` 且 `exit_reason` 非空、`closed_at` 在窗口内（days 1~180，默认 30）的
`trade_records` 行；`extra_filter` 为账号范围过滤（all / live / testnet / 账号 key，docs/17）。

### 2.1 总览指标（`_agg` + 扩展）

| 指标 | 定义 | 口径说明 |
|---|---|---|
| `count/wins/losses` | 闭仓数 / 盈利笔数（pnl>0）/ 亏损笔数（pnl<0） | Decimal 统一转 float 聚合 |
| `win_rate` | wins / count | **净胜率**，docs/24 A2 拍板主考核口径；不做 win_tp1/expired 之类口径美化 |
| `pnl` | Σ realized_pnl | 净盈亏 USDT |
| `avg_win / avg_loss` | 盈利均值 / 亏损均值（负值） | 无对应侧样本时为 0.0 |
| `payoff` | \|avg_win / avg_loss\| | 盈亏比，需双侧样本，否则 None |
| `ev_per_trade` | pnl / count | 期望值，**USDT/笔**（非 R 口径） |
| `total_fee / total_funding` | Σ fee_total / funding_total | 费用拆分 |
| `planned_risk_total` | Σ risk_amount | AI 开单时锁定的单笔风险合计 |
| `plan_gap` | max(0, \|净亏\| − 计划风险合计) | 计划 vs 实际：亏超计划部分，差额主要来自费用；≤0 钳为 0，前端 plan_gap>0.5 标注「亏超计划」 |
| `avg_hold_hours` | 平均持仓时长（小时） | closed_at − opened_at |
| `attributed` | attributed_at 非空笔数 | 已归因笔数 |

### 2.2 分组维度（维度 × 桶，每桶复用 `_agg` 指标）

| 维度 | 取值来源 | 说明 |
|---|---|---|
| 开单类型 | `ai_snapshot.trade_type` | 缺失归 `unknown` |
| 信号类型 | `signal_type` 经 `TRIGGER_FAMILY` 家族映射 | 同源常量与 `/review/stats` 共用；含旧管线别名（breakout/uptrend_pullback 等）；`trigger_candlestick`（纯金K）2026-09-29 下线仅历史行；NULL/未识别 → 「未记录」 |
| 方向 | `direction` | long / short / 未知 |
| 出场原因 | `exit_reason` | sl / tp1_then_sl / tp1_trail / trail_sl / breakeven_sl / manual / error 等 |
| 开仓时段 | `opened_at`+8h 落北京时间 4h 桶 | 6 桶（0-4 / 4-8 / … / 20-24 时） |
| 止损锚 | `ai_snapshot.stop_anchor` | structure（结构锚）/ near（近锚），docs/23/24 A5b：验证近锚单是否劣化 |
| 战法 | `ai_snapshot.tactic_name` | 2026-10-02 战法模块（仅借鉴标注，不影响开单结论）：按命中战法分组对比实盘胜率/EV——哪个战法真能打数据说话；未命中/旧行归「未指定」；`tactic_reason` 随 items 逐笔展示 |
| 金K形态 | `pattern` 列（trade_records 自有） | 2026-10-01-3 拍板：完整 12 金K固定顺序全量列出（0 笔也占行，12 维度齐全），看涨 6（锤/吞没/启明星/刺透/看涨孕线/蜻蜓十字）+ 看跌 6（流星/吞没/黄昏星/乌云/看跌孕线/墓碑十字），展示名取 `PATTERN_LABEL_MAP`；突破类无形态/旧行 NULL → 「未记录」 |
| 规则版本 | `rule_version` 或 `legacy` | docs/24 A0：同版本内分组对比才有证明力 |
| 评分分桶 | `ai_snapshot.recommendation` | <60 / 60~69 / 70~79 / 80~89 / >=90；TRADING_MIN_RECOMMENDATION=60 是开仓铁闸，分桶×盈亏交叉检验评分与后续盈亏的相关性（docs/24 D4）；展示按桶序显式排序 |
| 量比分桶 | `ai_snapshot.volume_ratio` | 缩量 <1.0 / 常量 1.0~1.2 / 放量 >=1.2；量比=信号K线量÷近20根中位量，1.0 缩量线（缩量突破无近锚资格 docs/23）、1.2 放量加分线（docs/24 A5b） |
| 错误标签 | `error_tags` 逐标签拆行 | 一笔多标签各计一次；仅统计已归因的 |

### 2.3 逐笔明细（`items`）

每笔输出：计划三价（`entry_plan/sl_plan/tp1_plan`，取 ai_snapshot）vs 实际成交
（`entry_actual/realized_pnl/pnl_pct`）、`risk_amount`、`fee_total/funding_total`、
`recommendation`、`stop_anchor`、`volume_ratio`、`rule_version`、`hold_hours`、
`error_tags/error_lesson`、`attributed`。前端明细行可展开交易复盘 K 线（TradeReplayChart）。

### 2.4 费用回补与 R 口径

- `backfill_costs(db, trader, limit=20)`：`fee_total` 为空的 CLOSED 行惰性回补——按
  symbol+opened_at 从交易所拉 income 明细，COMMISSION→fee_total、FUNDING_FEE→funding_total，
  回写后一次性生效不再查。账号解析按记录归属（account_key 缺失旧行按 testnet 回落，
  账号已移除时回落环境默认账号）；单轮 ≤20 笔防拉爆限额；失败按 0 落库避免反复重试。
  `/review/actual` 与归因任务调用前都会先回补。
- R 口径分布：实盘归因统计以 USDT 为主口径；R 倍数出现在两处——① 逐笔 R 泄漏对账
  （`trade_recon`，R = 金额 / risk_amount，见 §2.5）；② AI 建议质量口径的模拟期望值
  `ev_r`（§5.2，含费用假设的简化 R）。两者口径不同，勿混用。

### 2.5 逐笔 R 泄漏对账（`trade_recon.py`，衔接 docs/04）

背景（docs/24 A1 查因先行）：tp1_then_sl 出场单理论约 +0.75R、实际仅约 +0.04R，每笔约
0.7R 系统性泄漏。`reconcile_trade(db, rec)`（API `GET /api/trades/{id}/reconciliation`，
`backend/app/api/trades.py`）逐笔对照计划 vs 实际，把泄漏拆为五项（成本口径：不利=正）：

| 项 | 计算 |
|---|---|
| a 入场滑点 | sign × (实际成交 − 计划 entry) × 数量 |
| b 手续费 | \|fee_total\|（缺失时惰性查 income 回补） |
| c 资金费 | −funding_total（交易所负=支付→正成本） |
| d SL 穿价 | sign × (触发价 − 成交价) × 数量（取 SL_FILL 事件；当前结算流程不写该事件，常缺） |
| e TP1 滑点 | 由 TP1 分档盈亏反推实际成交均价，sign × (计划 TP1 − 反推成交) × 数量 |

汇总输出理论 R（tp1 档位占比 × RR1，余档保本 0）vs 实际 R：总泄漏 = 理论 − 实际，
covered = a~e 可得项之和，unexplained > 0.05R 时在 `gaps` 提示可能有未入账成本。
防御式约定：任一数据缺失对应项为 null 不抛异常，缺口以中文一句落 `gaps`
（含 TP1 实际成交数量与计划分批不符的检测，容差 1%）。

## 3. AI 归因

`backend/app/services/ai_attribution.py`：对已平仓交易，把「AI 当时的计划 + 实际结果 +
K 线特征」喂给 AI，输出结构化错误标签与一句话教训，落库 `trade_records` 的
`error_tags / error_lesson / attributed_at`。

- **事实由程序计算，AI 只做归因判断**：`build_facts(rec, klines)` 输出事实包——
  AI 计划（entry/sl/tp1/tp2、止损距离%、风险回报比）、实际结果（成交价/出场原因/盈亏/
  费用/持仓时长）、K 线特征（`entry_pos_in_20bar_range` 入场在开仓前 20 根区间中的位置，
  1=区间顶、0=区间底，>1/<0 表示越出区间即追高追空信号更强，不做截断；`mfe_pct/mae_pct`
  持仓期最大有利/不利波动；`held_bars`）、分析原文截 1500 字。
- **标签词表固定**（`ERROR_TAGS`，9 类）：追高追空 / 止损过宽 / 止损过窄 / 逆指标多数 /
  逆4h背景 / 区间中段开单 / 执行偏差 / 行情异常 / 无明显错误——保证分组统计口径一致；
  词表外标签丢弃，全部无效时兜底为「其他」。
- **调用**：`attribute_trade` 走 `settings.AI_MODEL`（temperature 0.2，max_tokens 32000——
  GLM 思考型 reasoning 计入配额，与 ai_analyzer 同口径），系统提示要求 tags 选 1~3 个、
  lesson 一句话 ≤80 字（代码截断 120 字），只输出 JSON。
- **幂等**：每笔仅归因一次（attributed_at 为幂等键），支持定时批量与手动单笔触发。
- **触发通道**：
  - 定时 `run_ai_attribution_task`（每小时 14 分，在结算/建议复盘之后）：取当前环境
    （DB `trading_testnet` 为运行时权威）下 CLOSED 未归因的最近 ≤5 笔
    （`ATTRIBUTION_BATCH=5`，每笔一次 LLM 调用控制开销），费用回补先行（事实包需要
    fee/funding）。AI 未配置（`AI_API_KEY` 空）静默跳过。
  - 手动 `POST /api/scans/review/attribute`：body 带 `trade_id` 归因指定单笔，缺省处理
    全部待归因（≤5 笔）；前端「一键归因」按钮。
- **K 线区间**：开仓前 ~100 根 + 持仓全程，上限 480 根（`review_tasks.run_ai_attribution`），
  与交易复盘 K 线接口同源。

## 4. 补丁体系（提案→审核→应用→评估→回滚）

`backend/app/services/patch_service.py`（docs/archive/12 §10）。AI 错误归因发现某规则性
错误标签高频出现 → 生成补丁草稿 → 人工确认合入 → 每日三态评估 → 页面一键回滚。

关键约束：

- 系统自带提示词（`SYSTEM_PROMPT` / `AGENT_SYSTEM` 代码常量）**永不改动**；提示词补丁是
  「覆盖规则」段，带 `<!-- patch:标签:id前8位 -->` 标记注释追加在
  `system_config.strategy_prompt` 尾部。
- 参数补丁写 `system_config` 参数列（NULL=默认语义）；回滚统一走 DB（提示词删标记段 /
  参数恢复 NULL），即时生效，无需重建容器。
- 「行情异常」「无明显错误」非规则性标签，不参与补丁触发（`RULE_TAGS`）。

### 4.1 触发（`run_trigger`，每日 11:40 / 手动 POST /review/patches/trigger）

三重门槛，全部写在 `skips` 返回里（任务记录与响应直接可见卡在哪关）：

1. **样本**：近 7 天已归因笔数 ≥ 8（`MIN_SAMPLE`）；
2. **热度**：标签热度（近 7 天该标签笔数 / 已归因笔数）≥ 0.5（`HEAT_THRESHOLD`）——
   相对占比可免疫开单量波动；
3. **去重与冷却**：同标签已有 draft/active 补丁不重复生成；同标签 14 天内合入过
   （任意终态）冷却跳过（`COOLDOWN_DAYS=14`）。

### 4.2 草稿生成（`_generate_draft`，程序校验通过才建 draft）

LLM 二选一输出：

- `kind="prompt"`：`old_text` 必须是系统提示词渲染结果（含风险预算文案）的**逐字子串**
  （≤300 字落库），`new_text` 为 ≤500 字可执行规则——校验不过不建草稿；
- `kind="param"`：`param_key` 限白名单 5 个（`max_stop_pct` 止损宽度硬上限 /
  `liq_gate_buffer` 强平闸门缓冲 / `min_adapt_leverage` 动态杠杆下限 /
  `pullback_market_pct` 入场偏离容差 / `max_slippage_pct` 开仓滑点实测上限），
  `param_value` 必须为比例值（0<v<1）。

草稿携带证据（`evidence_json`）：热度、样本量、典型案例 trade_id（≤5 笔）、当前参数、
生效中的其他补丁。

### 4.3 合入 / 回滚（页面操作）

- `apply_patch`：prompt → strategy_prompt 追加标记段；param → 写参数列。合入时快照
  合入前 7 天基线指标（`metrics_before_json`：热度/EV/胜率/建议通过率）。
- `rollback_patch`：prompt 删标记段（到下一标记/文末）；param 恢复 NULL。仅 active 及
  终态可回滚，draft 直接删除即可。
- `build_prompt_view`（`GET /review/prompt-view`）：当前生效提示词分层视图——系统自带
  （代码常量只读）/ 用户自定义段 / 补丁覆盖段（含 orphan 段识别：标记在但补丁行不在）+
  当前参数。

### 4.4 三态评估（`run_evaluate`，每日 11:45）

active 补丁按合入天数：≥7 天（`EVAL_FIRST_DAYS`）首评，≥14 天（`EVAL_FINAL_DAYS`）终评；
评估窗口已归因样本 <8 顺延观察（worse 除外）。`_judge` 判定顺序：

| 顺序 | 检查 | 阈值 | 结果 |
|---|---|---|---|
| 护栏三 | 建议通过率（AIAnalysis suggest 占比） | <30% | worse（补丁过严 = 系统被阉割） |
| 护栏一 | EV/笔 | 转负，或相对恶化 >30%（负基线同样适用） | worse |
| 护栏一 | 胜率 | 下降 >20pp | worse |
| 护栏二 | 其他标签热度 | 任一翻倍（镜像对盯防） | worse |
| 主指标 | 目标标签热度比（后/前） | ≤0.5 | valid（热度下降 ≥50%） |
| 主指标 | 同上 | 0.8~1.2 | invalid（无改善） |
| — | 同上 | 其余（改善未达 50%） | pending（继续观察） |

终评处理：worse 保持 active 并置顶告警（等人工回滚）；valid/invalid 定稿为对应 status；
14 天仍无结论按 invalid 处理。`window_stats` 的胜负口径与 actual_review 一致
（win = realized_pnl > 0）。

### 4.5 与 RULE_VERSION 的衔接

补丁合入即刻改变运行时规则（提示词/参数），但 `RULE_VERSION` 不自动递增——它由人工在
`backend/app/config.py` 维护，按「改 trigger / risk_guard / 提示词纪律 / 分批比例均算
改版」的约定 bump（如 v2026-09-29 → v2026-09-30 → v2026-10-01 均为金K/长实体门类规则
变更）。补丁验证有效后若沉淀为代码级规则，随下一次版本递增进入新基线，复盘统计自此按
新版本分组。

## 5. 数据模型 / API / 前端三面板

### 5.1 数据模型
