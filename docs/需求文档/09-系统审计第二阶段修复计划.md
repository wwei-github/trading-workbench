## 三、第二阶段任务（建议执行）

### 任务一：4h 三时刻资格与时效契约

现状事实：

- 扫描阶段无 4h 方向直接拒绝，口径明确。
- 分析阶段 4h 获取失败只打降级标记；`apply_htf_constraint` 在 `not htf_klines` 时**原样返回 suggest**（[technical.py](../../backend/app/services/strategy/technical.py#L1051-L1056)）。
- 执行层只把 `htf_phase` 写入快照供复盘，**不做时效复核**（[trade_engine.py](../../backend/app/services/trade_engine.py#L214-L217)）。

风险：扫描到实际开仓之间可能跨越 4h 收盘与状态切换；分析缺数时等于绕过唯一的 4h 趋势门。缺数标记不是执行保护。

实现要求：

- [x] 定义三个时刻的契约：扫描（必须新鲜 4h，缺数拒绝）、分析（允许使用最近已收盘快照并记录 `htf_as_of`，缺数时 `suggest` 降级为禁止新开仓）、执行（按 `htf_as_of` 与当前时间计算陈旧度，超过阈值禁开）。
- [x] 执行层复核使用与扫描、兜底同一个 `STATE_ALIGNED` 常量，不引入第二套状态口径。
- [x] 缺数、超时、陈旧三种情况分别落明确原因码，写入决策快照，便于复盘归因。
- [x] 测试覆盖：分析缺数、4h 快照陈旧、扫描后状态切换、执行复核通过四条路径。

验收：同一信号在 4h 缺数或陈旧时不可能进入开仓；所有拒绝都有可解释原因码。

### 任务二：评分档位硬校验

现状事实：`recommendation` 被 clamp 到 50–100 的连续值（[risk_guard.py](../../backend/app/services/risk_guard.py#L486-L505)）。提示词要求 60/70/85 三档，但 58 分可以 suggest，也可能被静态门槛拦成隐藏弃单；提示词内“只取三档”与“同档上下限”的表述也不一致。

待拍板：非档位分如何处理。

- 方案 A（推荐）：归一到最近档位，同时保留 `recommendation_raw` 落库，用于后续校准分析。优点是不丢失有效信号，统计口径确定。
- 方案 B：直接拒单。口径最严，但会把模型输出抖动放大成弃单，可能损失样本。

实现要求：

- [x] 校验层统一归一或拒绝逻辑，禁止连续分直接进入执行链。
- [x] `recommendation_raw` 进入决策快照，复盘可按原始分与档位分别统计。
- [x] 提示词文案统一，删除“同档上下限”与“只取三档”的冲突表述。
- [x] 测试覆盖：58→60、72→70、88→85、越界值、非法值。

验收：执行链只出现 60/70/85；每个被降档或拒绝的样本都能在快照中看到原始分。

### 任务三：风险字段口径拆分

现状事实：模型只有一个 `risk_amount`（[trade.py](../../backend/app/models/trade.py#L89)）；成交滑点导致实际风险超计划 15% 仅告警，记录仍用成交前参考风险；部分止盈后该字段不随剩余仓变化。

目标字段（命名可按现有风格微调）：

- `planned_risk`：下单前的计划风险。
- `initial_risk`：成交后按实际成交价与止损计算。
- `remaining_risk`：当前剩余仓对应风险，随 TP/减仓更新。
- `realized_net`：已实现净收益（含费用口径后续接入）。

实现要求：

- [x] 幂等迁移新增字段，旧数据按 `risk_amount` 回填，`risk_amount` 保留一段读取兼容期，统计与前端逐步切换。
- [x] 开仓、TP1/TP2、减仓、平仓各路径同步更新 `remaining_risk`。
- [x] 复盘 R 口径统一改用 `initial_risk`（计划口径另列），避免同一字段承担多个分母。
- [x] 测试覆盖：滑点超预算、TP1 部分止盈、TP2、手动减仓、平仓。

验收：任何一笔交易都能同时回答“计划风险、成交初始风险、当前剩余风险、已实现净收益”。

### 任务四：组合热度改用剩余风险

现状事实：热度仍为 `sum(risk_amount × beta)`（[trade_engine.py](../../backend/app/services/trade_engine.py#L1636-L1643)），TP1 后原始风险不缩小，热度被高估；方向集中度与 BTC 因子暴露也未分开。

实现要求：

- [x] 热度输入切换到 `remaining_risk`。
- [x] 总止损风险、方向集中度、BTC 因子暴露分列计算，不再共用一个“热度”含义。
- [x] 保留原口径只作为日志/告警对照，不再作为闸门依据。
- [x] 测试覆盖：部分止盈后放行、同向多单集中度、beta 缺失回落 1.0。

验收：组合闸门反映当前剩余风险，而不是开仓时的历史风险。

### 任务五：统一决策版本（第二批）

现状事实：缓存指纹已纳入 `RULE_VERSION` 与配置摘要，但补丁合入仍不产生统一决策版本，参数回滚也不等价于恢复此前任意自定义值（[patch_service.py](../../backend/app/services/patch_service.py)）。

实现要求：

- [x] 补丁合入、配置变更、提示词变更在同一事务内生成统一 `decision_version`。
- [x] 决策快照记录该版本，复盘与缓存按版本分组。
- [x] 回滚记录恢复来源值，不只回落到 NULL/默认。

验收：任意一笔决策都能还原当时的规则版本、配置摘要、提示词与缓存来源。

## 四、暂不执行

- **基线对照体系（7.2）**：先做最小地基——冻结版本、统一扣费 R 口径、按 `ab_bucket`/版本分组打标签。完整对照平台等前向样本，避免现在用同一批历史数据反复调参。
- **回踩扣分调整（5.1）**：审计未证实扣分过严，需按触点、反向票数、质量分、入选率与后续表现做对照后再动。
- **模块删减（第六章、第四阶段）**：没有同版本前向样本前不删双评委、P1、战法与归因补丁，保留开关与统计隔离。
- **订单状态机重构（7.3）**：第一阶段已覆盖保护失败与紧急平仓失败。剩余“订单已提交但响应丢失”由现有对账任务承接，补故障注入测试验证即可。

## 五、执行顺序与验收

1. 任务一（4h 契约）：资金安全优先，单独提交，便于回滚。
2. 任务二（档位校验）：纯校验层改动，独立提交。
3. 任务三 + 任务四：共享一次模型迁移，同批提交；先跑旧数据回填与统计口径回归。
4. 任务五、任务六：第二批，归因与文档同步。

统一验收要求：

- 每个任务先写失败测试，再改实现。
- 默认口径仍以扣费后的真实交易账本为准，回放只作反事实参考。
- 不以单一行情窗口的改善作为通过标准；新口径必须能在历史样本上解释差异来源。
- `git diff --check` 通过，相关回归测试全绿。
