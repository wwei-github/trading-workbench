# 12. 复盘系统重设计：实盘归因主轴

> 2026-09-18 | 状态：已实现，待部署 | 前置文档：07（全链路）、11（现行规则总览）

## 1. 背景与问题

### 1.1 旧复盘为什么没用

| 组件                      | 现状                                                                      | 问题                                                                           |
| ------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 模拟回放（trade_reviews） | 定时任务在跑，表 0 行                                                     | 上线不足 24h，建议未满观察期；且口径是「全部 AI 建议、零费用模拟」，与实盘脱节 |
| 复盘统计面板              | **从未挂载**（ScanResult.tsx 只有孤儿 import，资金划转 Tab 改造时被挤掉） | 前端根本没有复盘入口                                                           |
| 交易K线回放图             | 有用                                                                      | 只服务单笔查看，无统计归因                                                     |

### 1.2 真正的痛点

实盘 6 笔 5 亏 **-400 U**（3 止损 + 2 强平 + 1 TP1），但系统没有任何东西回答「亏在哪类单子、下次怎么避」。

典型案例（4USDT，2026-09-17）：

- 计划亏 60 → 实际亏 **65.89**（手续费 0.71 + 资金费 2.98，单笔资金费即 0.21% 名义）
- 止损距离 4.2% 贴着旧强平闸门上限 4.5% 通过（闸门写死 MMR=0.5%，该币实际 1.5%）→ 持仓 6h 被强平，SL 永远不会成交
- 以上偏差**没有任何复盘机制捕捉**，只能人工翻流水发现

### 1.3 设计决策（用户拍板）

1. **复盘对象转向**：从「模拟回放 AI 建议」转向「实盘交易 + 计划对照」
2. **全量方案**：实盘归因 + 页面重构 + 模拟 EV 费用修正 + **AI 错误归因**（每笔平仓后 AI 出错误标签）
3. 模拟回放不删除：重新定位为「不受开仓闸门影响的 AI 水准测量」（AI 说 suggest 但被闸门拦截的单子，模拟回放能回答「拦对了还是拦错了」）

## 2. 总体架构

```
                    ┌─ 每小时第10分 建议模拟回放（原有，表 trade_reviews）
beat 调度 ──────────┤
                    └─ 每小时第14分 AI 错误归因（新增）
                              │
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                      ▼
  结算落库(trade_engine)   费用回补(惰性)        LLM 归因
  fee_total/funding_total  income API 拉取     build_facts(程序硬事实)
                                                  → attribute_trade(AI 判断)
                                                  → error_tags/error_lesson
        │
        ▼
  GET /api/scans/review/actual  ←──── 复盘 Tab·实盘归因（默认页）
  GET /api/scans/review/stats   ←──── 复盘 Tab·AI建议质量（副页，EV 修正）
  POST /api/scans/review/attribute ←── 手动触发归因（单笔/批量≤5）
```

## 3. 数据模型

### 3.1 trade_records 新增列（幂等迁移，database.py `_run_migrations`）

| 列              | 类型          | 说明                                                |
| --------------- | ------------- | --------------------------------------------------- |
| `fee_total`     | NUMERIC(20,6) | 手续费合计（负值），结算时从 COMMISSION income 聚合 |
| `funding_total` | NUMERIC(20,6) | 资金费合计，结算时从 FUNDING_FEE income 聚合        |
| `error_tags`    | JSON          | AI 归因错误标签数组（中文标签，1~3 个）             |
| `error_lesson`  | TEXT          | AI 归因一句话教训（≤120 字）                        |
| `attributed_at` | TIMESTAMP     | 归因时间（NULL=待归因，幂等键）                     |

### 3.2 存量数据

- 旧平仓单 fee/funding 为 NULL → `backfill_costs` 惰性回补（按 symbol+opened_at 拉 income API，单轮 ≤20 笔，失败按 0 兜底不阻塞统计）
- 无归因的行 attributed_at 为 NULL → 定时任务逐步补齐（≤5 笔/轮）

## 4. 实盘归因统计（actual_review.py）

### 4.1 总览卡

胜率（净盈亏>0 占比）/ 盈亏比（avg_win/|avg_loss|）/ 期望值每笔（pnl/count）/ 平均持仓时长 / 费用拆分。

**计划 vs 实际对照**（核心）：

```
plan_gap = min(pnl, 0) + planned_risk_total
```

- `planned_risk_total` = Σ risk_amount（AI 开单时锁定的单笔风险）
- `plan_gap > 0` 表示亏超计划 → 明细归因到手续费/资金费/滑点
- 4USDT 案例：计划 60，实际 65.89，gap 5.89 = 费用 0.71 + 资金费 2.98 + 价差

### 4.2 分组维度（按真实差异分，哪组亏收紧哪组）

| 维度     | 取值来源               | 用途                          |
| -------- | ---------------------- | ----------------------------- |
| 开单类型 | ai_snapshot.trade_type | 某打法全亏 → 提示词收紧该打法 |
| 方向     | direction              | 多/空偏科检查                 |
| 出场原因 | exit_reason            | 强平/止损集中度               |
| 开仓时段 | opened_at+8h 后 4h 桶  | 北京时段效应                  |
| 错误标签 | error_tags（拆行）     | AI 归因结论的量化聚合         |

### 4.3 API

`GET /api/scans/review/actual?days=30` → `{overview, groups[], items[]}`

items 每行含：计划三价（entry_plan/sl_plan/tp1_plan）vs 实际成交、realized_pnl、pnl_pct、fee_total/funding_total、hold_hours、error_tags/error_lesson、attributed。

## 5. AI 错误归因（ai_attribution.py）

### 5.1 设计原则

- **标签词表固定**（9 项），保证分组统计口径一致：

| 标签         | 判定要点                               |
| ------------ | -------------------------------------- |
| 追高追空     | 入场位置差：价格已远离关键位后追入     |
| 止损过宽     | 止损距离过大，风险占用过高甚至强平风险 |
| 止损过窄     | 太贴近入场价被正常波动扫掉             |
| 逆指标多数   | 开仓方向与指标多数决相悖               |
| 逆4h背景     | 与 4h 大级别趋势/均线排列相反          |
| 区间中段开单 | 价格处盘整区间中部，无边缘/突破确认    |
| 执行偏差     | 滑点/手续费/资金费侵蚀超计划           |
| 行情异常     | 突发消息或极端波动，计划内无法预见     |
| 无明显错误   | 计划内亏损：纪律无失，行情未走出       |

### 5.2 事实包（程序算硬数据，AI 只做归因）

`build_facts(rec, klines)` 输出：

- **plan**：AI 计划三价、止损距离 %（按计划价口径，与风控校验一致）、RR
- **actual**：实际成交、exit_reason、realized_pnl/pnl_pct、fee/funding、持仓时长
- **kline_facts**：
  - `entry_pos_in_20bar_range`：入场在开仓前 20 根区间中的位置（1=区间顶，多头追高；**不截断**，>1 表示入场越出区间，追高信号更强）
  - `mfe_pct`/`mae_pct`：持仓期间最大有利/不利波动（按实际成交价）
  - `held_bars`：持仓 K 线数
- ai_analysis 前 1500 字（AI 当时的判断原文）

K 线区间：开仓前 ~100 根 + 持仓全程（与交易复盘K线接口同源），上限 480 根。

### 5.3 LLM 调用

- system prompt 注入词表定义 + 「事实优先于推测」「只输出 JSON」约束
- `temperature=0.2`，`max_tokens=12000`（GLM 思考型配额口径，同 ai_analyzer）
- 返回 `{tags, lesson}` 经词表白名单过滤（非法标签剔除，空则落「其他」）

### 5.4 任务

- **定时**：beat `ai-attribution` 每小时第 14 分（排在第 10 分结算/建议回放之后），待归因为空不记任务记录避免刷屏；AI_API_KEY 为空静默跳过
- **手动**：`POST /api/scans/review/attribute`，body `{trade_id?}`（缺省批量 ≤5）；前端复盘页「AI 归因」按钮显示待归因数
- 单轮 `ATTRIBUTION_BATCH=5`（每笔一次 LLM 调用，控开销与时长）
- 幂等：归因前先查 attributed_at IS NULL；手动指定单笔时忽略幂等强制重跑

## 6. 模拟回放 EV 口径修正（review/stats）

旧口径只看胜率，无费用概念 → 模拟胜率虚高误导。修正为 R 倍数期望值：

```
loss:      -1R
win_tp1:   +|tp1-entry|/|entry-sl| R
win_tp2:   +|tp2-entry|/|entry-sl| R
费用(R) = (0.001 + 0.0003 × floor(bars/8)) / (stop_dist/entry)
          └ taker 往返 0.1% ┘└ 资金费 0.03%/8h 按持仓K线折算 ┘
ev_r = r_mult - 费用(R)
```

整体与每个分组均输出 `ev_r`；前端 AI 建议质量面板加期望值卡与列（>0 绿 / <0 红）。

## 10. 后续设计：归因标签 → 提示词自动迭代闭环

> **实现状态（2026-09-18）**：本节已全量实现并部署。与设计的偏差：
> - 判定列独立为 `prompt_patches.verdict`（pending/valid/invalid/worse），status 只管生命周期
> - 评估窗口样本不足（<8 笔已归因）时顺延观察，不判定（防空窗口误判）
> - API 增加 `POST /review/patches/trigger`（手动触发草稿生成）与 `DELETE /review/patches/{id}`（删草稿）
> - 参数补丁可经「策略配置」面板手改（max_stop_pct / liq_gate_buffer，留空=默认），与补丁回滚共用同一列
> - EV 恶化判定对负基线同样适用：`(ev_b−ev_a) > 30%×|ev_b|` 或 EV 转负

> 拍板（2026-09-18）：时段细化与滑点拆细不做；本条为唯一后续方向，设计如下（已实现）。

### 10.1 目标

把「错误标签统计」从**人看报表**升级为**系统自动改规则**：某类错误标签持续高频出现 → 说明对应环节的规则有漏洞 → 自动生成提示词补丁建议 → 用户确认后生效。

### 10.2 触发判定（新增定时任务，建议每日一次）

在实盘归因数据上定义「标签热度」：

```
tag_heat(tag) = 近7天该标签出现笔数 / 近7天已归因总笔数
```

- **告警阈值**：`tag_heat ≥ 0.5` 且近 7 天已归因 ≥ 8 笔（样本不足不误报）
- **冷却**：同一标签 14 天内不重复告警（防止连续刷屏）
- 排除「无明显错误」「行情异常」两个非规则性标签（它们不指向规则漏洞）

触发后在任务记录里产出一条「规则补丁建议」（不入库 system_config，只输出待确认），附带证据：标签明细笔数、典型案例 trade_id、当前提示词对应段落原文。

### 10.3 标签 → 环节映射（补丁落点固定，避免 AI 自由发挥）

| 高频标签     | 漏洞环节             | 补丁落点                                                                           |
| ------------ | -------------------- | ---------------------------------------------------------------------------------- |
| 追高追空     | 筛选管线入场位置检查 | ai_analyzer/ai_agent SYSTEM_PROMPT 入场纪律段                                      |
| 止损过宽     | 风控校验             | **程序参数** `max_stop_pct`（system_config 新列，开仓闸门读取；默认空=不限）       |
| 止损过窄     | 提示词止损指导       | SYSTEM_PROMPT 止损段                                                               |
| 逆指标多数   | 提示词多数决权重     | SYSTEM_PROMPT 指标多数决段（或 Agent AGENT_SYSTEM 规则5/7）                        |
| 逆4h背景     | 同上                 | 同上（4h 背景相关句）                                                              |
| 区间中段开单 | 筛选管线触发确认     | SYSTEM_PROMPT 触发条件段（或 trigger.py 收紧，程序侧）                             |
| 执行偏差     | 开仓闸门             | **程序参数** `liq_gate_buffer`（system_config 新列，默认 0.005，现值常量化为可配） |

**补丁落点统一为 DB**（2026-09-18 补充，应用户要求全页面操作、不碰 git）：程序侧两类补丁不产代码 diff，而是收敛为 system_config 可配参数——AI 补丁只「建议参数值」（如 max_stop_pct=4.0%），人工确认后写入 DB，程序每次开仓实时读取。回滚 = 参数恢复默认/置空，同样页面操作、即时生效。映射表中 trigger.py 收紧一类落点仅当参数化不可达时才走代码（届时按普通功能开发，不属补丁闭环范畴）。

### 10.4 补丁生成与生效流程

**补丁是「覆盖规则」不是「改写原文」**（2026-09-18 修正）：系统自带提示词（SYSTEM_PROMPT / AGENT_SYSTEM）硬编码在代码里，是唯一真源、页面只读展示、永不改动。提示词类补丁的实际形态 = 一段带标记的覆盖规则，追加到 `system_config.strategy_prompt` 尾部（该字段本就注入管线且**位于系统提示词之后，对模型优先级更高**）。AI 生成的 diff 语义是「针对系统提示词某段（old_text 仅作展示引用）→ 追加覆盖规则（new_text）」。

1. 定时任务触发 → 用 AI 生成补丁草稿：输入 = 高频标签 + 证据 + 系统提示词对应段落原文，输出 = 覆盖规则文本（程序校验：必须含 `<!-- patch:{target_tag} -->` 标记，单段 ≤500 字）
2. **人工确认**：复盘页「规则补丁」子页审阅草稿（含系统原文段落对照）→ 点「合入」追加到 strategy_prompt——**不让 AI 直接改任何提示词**
3. 合入后进入评估观察期，效果判定与回滚细则见 §10.6

### 10.5 明确不做

- 不做全自动生效（提示词是系统核心，改错代价大，必须人审）
- 不做时段细化分组、不做滑点拆细（已拍板不做；fee/funding 已落库够用）
- 样本 < 8 笔不触发任何建议（当前开单频率下预计需 2~4 周才有首批可分析数据）

### 10.6 补丁效果度量与回滚

#### 三层指标（评估任务每日跑，合入后第 7 天首评、第 14 天终评）

| 层     | 指标                                                              | 防什么                                         |
| ------ | ----------------------------------------------------------------- | ---------------------------------------------- |
| 主指标 | 目标标签热度：合入前 7 天 vs 合入后 7 天（等长窗口，各自样本 ≥8） | 直接回答「修没修好」                           |
| 护栏一 | 总体 ev_per_trade、胜率                                           | 修好 A 不能把整体做差                          |
| 护栏二 | 其他规则性标签热度（重点盯镜像对：止损过宽↔止损过窄）             | 按下葫芦浮起瓢                                 |
| 护栏三 | 建议通过率（suggest 占分析总数）                                  | 补丁过严 → AI 大量 skip——「没有错误」≠「变好」 |

热度用相对占比（该标签笔数/已归因笔数）而非绝对笔数，天然免疫开单量波动。

#### 三态判定

- **有效**：目标热度相对下降 ≥50%（或绝对值 <0.2）且三层护栏全部不劣化
- **无效**：目标热度变化 <±20%；第 7 天标记，第 14 天仍如此 → 建议回滚或换映射表落点环节
- **恶化**（任一即触发告警）：
  - ev_per_trade 由正转负，或相对跌幅 >30%
  - 胜率跌幅 >20 个百分点
  - 建议通过率跌破 30%（AI 几乎全 skip，补丁实际是阉割了系统）
  - 任一护栏标签热度翻倍

#### 恶化了怎么操作

**不自动回滚**（与生效须人审同一原则）：恶化触发 → 任务记录 + 复盘页出告警（附三层数据对照）→ 人工确认后**页面一键回滚**。

**回滚统一走 DB，无需 git**（补丁落点已全部参数化，见 §10.3）：

| 补丁类型   | 存储                                                                                                                 | 回滚方式                                                                | 生效                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------- |

**API**：

- `GET /api/scans/review/patches` → 列表（含 metrics_before/after 已算好的对照行）

- `POST /api/scans/review/patches/{id}/rollback` → 回滚（恢复 old_text/默认参数，status→rolled_back）
