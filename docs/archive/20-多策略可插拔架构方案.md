## 一、设计目标与核心原则

### 1.1 要解决的问题

1. 新策略（EMA 趋势、策略 A 等）与现有「金K + AI」逻辑耦合在同一管线，无法独立开关、独立归因、独立风控预算；
2. 多策略并发缺乏明确规则：信号重叠、风险叠加、止盈止损/配置差异无统一处理框架；
3. 未来接入第三策略需再动存量代码。

### 1.2 核心原则（四条铁律）

1. **策略 = 信号生产者，系统 = 信号消费者**。策略只回答「何时开、开哪个方向、三价、理由、自评置信度」；风控、仓位、执行、出场骨架、复盘全部由系统统一承载。
2. **存量管线降级为内置插件**：现有「金K候选 → AI 三价」重构为 `golden_k_ai` 策略，EMA 策略为第二个插件 `ema_trend`。重构铁律：**golden_k_ai 输出与现状逐字段一致**，基线等价性测试锁死，存量行为零变化。
3. **协议从两个具体策略归纳（rule of two）**：接口字段必须两个策略都用得上才准进协议；第三个策略出现前不预设。不做通用「策略市场」式过度抽象。
4. **骨架不可变，参数可声明**：同根 K 线保守序、滞后一根生效、只收紧不放松等出场铁律硬编码在引擎骨架内，策略只能声明参数（ExitSpec），不可触碰骨架逻辑。

### 1.3 系统命名与双系统管理拍板（2026-10-10）

**命名**（与代码 id 一致，朴素描述性命名）：

- **金K·AI 系统**（`golden_k_ai`，内置）——金K 形态 + AI 评审的原生管线（docs/01-06 全链）；
- **EMA 趋势系统**（`ema_trend`，插件）——4H EMA144 闸门 + 1H 结构回踩/金叉的纯规则趋势跟踪（docs/19）。

**管理架构**：确认「共享底盘 + 双大脑」——两套系统的信号生产完全独立（各自的筛选判定/信号链），但执行引擎（trade_engine）、全局风控（熔断/组合热度/同向上限/普跌闸门）、复盘归因（按 strategy_id 分账）**共享同一底盘**。明确否决「两套完全独立的系统」：独立执行会导致全局风控各自记账（实际敞口翻倍）、执行/巡检/多账号代码翻倍、复盘分裂。

**双系统开关与使用形态**：

| 形态 | 现状（S1，零改动） | S2 之后 |
|---|---|---|
| 双系统并行 | 金K·AI 实盘交易 + EMA 趋势影子记录（现状即并行） | EMA 趋势接入执行，独立预算/风险权重 |
| 只用金K·AI | registry 不配 ema_trend 或 enabled=false（默认态） | 同左；EMA 趋势条目停用即回单系统 |
| 只用 EMA 趋势 | 做不到（开单权限未解锁） | 需 **S2 对称性增补：金K·AI 的开单可停用**（registry 中 golden_k_ai 条目 enabled 可编辑，trade_engine 开仓前检查；扫描任务仍恒跑——EMA 趋势币池与 L1 观测依赖其 universe），见 §八 S2 行 |

防火墙（两系统同时交易时，§4.2/§五 全部适用）：跨策略同标的互斥、方向对锁禁止、重叠率 >50% 只跑其一、策略级 max_positions 只是全局预算子集。

## 二、总体架构

```text
┌─────────────────────── 策略层（隔离，互不可见）───────────────────────┐
│  golden_k_ai 插件                ema_trend 插件         未来插件…      │
│  ├ 筛币/预筛（AI 候选）           ├ 筛币/预筛（评分卡）                  │
│  ├ 信号触发（金K触发器）          ├ 信号触发（均线/发散/缠绕）            │
│  ├ AI 三价分析（私有实现）        ├ 纯规则三价                           │
│  └ 私有参数 config{}             └ 私有参数 config{}                    │
└──────────────────────────┬───────────────────────────────────────────┘
                           │ 统一协议 StrategySignal
┌──────────────────────────▼───────────────────────────────────────────┐
│                      系统底座（共用，全局唯一）                        │
│  ┌ 调度层：strategy_registry 遍历 enabled 策略，独立产候选/信号        │
│  ├ 冲突仲裁：同标的互斥 / 策略级预算子集划分 / 全局风控铁律            │
│  ├ 执行层：trade_engine 下单/撤单/仓维护/trader 多账号扇出            │
│  ├ 出场引擎：全局唯一骨架 + per-position ExitSpec 参数解析            │
│  └ 复盘/归因：strategy_id 维度统计、AI 快照、前端图表                 │
└──────────────────────────────────────────────────────────────────────┘
```

**共用与隔离清单**：

| 共用（底座） | 隔离（策略私有） |
|---|---|
| 行情数据（market_data） | 候选生成与预筛逻辑 |
| 指标库（technical.py 全部 analyze_*） | 信号触发逻辑（触发器 / 评分卡） |
| 执行层（trade_engine 下单/撤单/仓维护/trader 扇出） | 策略级预算与开关 |
| 全局风控（账户熔断/保证金/在跑上限/同向上限） | 出场参数（ExitSpec per strategy） |
| 出场引擎骨架（保守序铁律） | 归因统计（strategy_id 维度） |
| 复盘 / AI 快照 / 前端图表组件 | 策略私有 raw 快照字段 |
| 黑名单 / 新币冷却 | 信号冲突拒绝记录 |

## 三、StrategyPlugin 协议

```python
@dataclass
class StrategySignal:
    # 与现有 AIAnalysis 三价对齐——trade_engine 消费的唯一形态
    strategy_id: str            # "golden_k_ai" / "ema_trend"
    symbol: str
    direction: str              # long / short
    entry: float
    stop: float
    tp1: float
    tp2: float                  # 0 = 无
    reason: str                 # 入场理由（触发器文案 / 信号描述）
    confidence: float           # 策略自评 0~1（AI 置信度 / 规则强度）
    raw: dict                   # 策略私有快照（votes / 震荡分 / 结构位…，落库归因用）

class StrategyPlugin(Protocol):
    id: str
    display_name: str
    def scan_candidates(self, universe: list[str]) -> list[Candidate]: ...
        # 筛币 + 预筛（策略私有过滤：评分卡 / 波动率闸门…）
    def build_signal(self, candidate: Candidate) -> Optional[StrategySignal]: ...
        # golden_k_ai：此步调 AI 分析；ema_trend：纯规则产出
    def exit_spec(self) -> dict: ...
        # 出场语义声明，给 trade_engine 与 backtest_engine 共用
```

关键解耦点：**trade_engine / 风控 / 复盘只认 `StrategySignal` 与 `strategy_id`，策略之间完全不可见**。AI 分析是 golden_k_ai 的内部实现细节，对系统其余部分透明——ema_trend 不调 AI，底座不感知差异。

## 四、单策略 vs 多策略：模式设计

### 4.1 结论：不存在两套代码，配置即并发度

`strategy_registry` 的 enabled 列表长度 = 并发数。只启用一个 = 单策略模式；启用多个 = 多策略模式。**分阶段解锁的是开单权限，不是架构能力**：

| 阶段 | 开单并发 | 说明 |
|---|---|---|
| S0 | 1（仅 golden_k_ai） | 归因地基，行为零变化 |
| S1 影子 | 1 开单 + N 产信号 | ema_trend 影子跑，天然收集重叠率数据 |
| S2 | ≤2（影子期数据放行） | ema_trend 独立预算 1-2 仓 |
| S3+ | 数据说话 | 相关性达标再放开更多策略 |

### 4.2 并发准入的量化铁律（预注册）

影子期统计两策略的：

- **信号重叠率**：同标的同方向同周窗口内都出信号的频率；
- **盈亏相关性**：逐周 R 序列相关系数。

**判定**：重叠率 >50% 或相关系数 >0.7 → 两策略实为「同一策略的两种参数化」，并发 = 放大回撤而无分散收益，**只跑其一**（选期望 R 高者）。两个策略若连回撤都同涨同跌，分开跑只是自欺。

## 五、重叠处理（三层规则）

| 层 | 场景 | 第一版规则 | 进阶（预注册后启用） |
|---|---|---|---|
| 信号重叠 | 同标的同方向，两策略都出信号 | **跨策略同标的互斥**：同 symbol 全系统仅一仓，后到信号拒绝并落库（reason=strategy_conflict）。先到先得，简单可靠 | 高置信度可置换：新信号 confidence 显著高于在跑仓（差值阈值预注册）且在跑仓浮亏 → 平旧开新 |
| 方向重叠 | 同标的多空对锁 | **禁止**（单仓模型天然排除；对锁是净持仓为零的伪对冲，费用双份） | 不做 |
| 风险重叠 | 不同标的同时回撤 | 全局风控兜底：周/月熔断、账户在跑上限、同向上限**对所有策略生效**；策略级 max_positions 只是全局预算的**子集划分**，不是额外额度 | 组合层面回撤归因（分策略 R 序列进复盘） |

**重叠率是资产不是麻烦**：S1 影子期把重叠率当核心观测指标落库——它回答「这两个策略是否值得同时存在」。数据判断，不拍脑袋。

## 六、止盈止损方案不同：ExitSpec per strategy

出场引擎是**每根 K 线轮询所有在跑仓位的 per-position 状态机**——每个仓位按自己的 `strategy_id` 解析 ExitSpec，天然互不干扰。改造点仅在「参数解析处」，骨架零改动：

```text
Trade.strategy_id ──→ ExitSpec(strategy) ──→ 出场骨架（全局唯一）
                                            ├─ tp_ladder: golden_k=60/20/80 可配 | ema_trend=无/实验结论
                                            ├─ be_arm:    golden_k=TP1 成交武装 | ema_trend=1×ATR 武装
                                            ├─ trail:     golden_k=swing3+ATR_k  | ema_trend=ATR×2
                                            └─ sig_exit:  golden_k=无           | ema_trend=破EMA55 等
```

关键约束：

1. **骨架不可变**：同根 K 线保守序（逆侧整根优先 / 顺侧近者先成）、滞后一根生效、只收紧不放松——硬编码在骨架内，策略不可触碰；
2. golden_k 的全部既有出场行为经基线等价性测试锁死；
3. `backtest_engine.replay_exit` 增加 `exit_spec` override 键——任一策略的出场语义直接可回测，出场方案之争（分批 vs 纯跟踪）全部交给配对实验。

## 七、配置参数不同：两级配置命名空间

配置从「全局平面」重构为「**全局层 + 策略层**」：

| 层 | 内容 | 变更方式 |
|---|---|---|
| 全局层（账户级，共享） | 风险额基数、周/月熔断阈值、在跑/同向上限、黑名单、TP 分批比例 | 现有 system_config 页面，不动 |
| 策略层（私有，隔离） | 各策略自有参数：ema_trend 的评分卡阈值/发散度/ADX 下限；golden_k 的触发器开关/触点引用/新币冷却 | `strategy_registry` JSON 内嵌 `config` 字段 |

```json
"strategy_registry": [
  {"id": "golden_k_ai", "enabled": true, "max_positions": 3, "risk_weight": 1.0, "config": {}},
  {"id": "ema_trend", "enabled": true, "max_positions": 1, "risk_weight": 0.5,
   "config": {"adx_min": 20, "divergence_min": 0.5, "range_score_max": 2}}
]
```

规则：

1. 策略私有参数**只进自己 namespace**，golden_k 感知不到 ema_trend 的参数，反之亦然（代码层：每插件一个 config dataclass，registry 反序列化注入，未知键拒绝）；
2. `risk_weight` 乘进单笔风险额：新策略上线先半风险运行（0.5），表现达标升 1.0——**风险驯化通道**；
3. 现有全局配置（TP 比例等）S0 阶段名义上归入 golden_k_ai 名下，实际存储位置不变（避免迁移风险），文档口径归属即可；
4. 策略级预算是全局账户预算的**子集划分**：`Σ(策略在跑仓) ≤ 账户在跑上限` 恒成立。

## 十、明确不做

1. **不做策略间信号仲裁市场**（如「两策略都出多信号则加仓」）——第一版同标的互斥已够，叠加规则等数据；
2. **不做策略对冲/对锁**——伪对冲；
3. **不做每策略独立账户**——账户扇出已存在（trader 多账号），策略维度再分账户会爆炸；单账户内子预算即可归因；
4. **不做动态权重分配**（按近期表现自动调 risk_weight）——过拟合温床，人工季度评估改；
5. **不为插件化而过度抽象**——接口字段必须两个策略都用得上才准进协议。

## 十一、风险清单

| 风险 | 缓解 |
|---|---|
| S0 重构动摇存量链路 | 基线等价性测试（终局逐例）+ 快照逐字段对比双保险；重构 PR 不夹带语义改动 |
| 双策略风险敞口叠加超预期 | 策略级是子预算非额外额度（§7.4）；上线首月 ema_trend 单仓位 + risk_weight=0.5 + 账户级上限不变 |
| 同标的冲突规则引发「先到占坑」低质量持仓 | 冲突拒绝落库统计；若 S2 后数据显示占坑率异常，补「高置信度可置换」规则（预注册后启用） |
| 两策略实为同质（伪分散） | §4.2 量化铁律：重叠率/相关性不达标即只跑其一 |
| 出场语义分流破坏保守序铁律 | ExitSpec 只许改参数不许改骨架；保守序判定在引擎骨架内硬编码 |
| registry 配置误操作（错改预算/误禁策略） | 配置变更落审计日志；enabled=false 立即生效但在跑仓不受影响（只停新仓） |

## 十二、一句话总结

**策略是插件，系统是宿主**：策略只产信号（统一 StrategySignal），底座统一管风控/执行/出场/归因；单策略还是多策略由 registry 配置决定而非代码分叉；并发与否、出场方案之争，全部交给影子期的重叠率/相关性数据和配对回测来裁决。
